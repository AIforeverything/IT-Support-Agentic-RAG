# Explanation of `config.py`

Your `config.py` file implements a centralized configuration management system for your Enterprise IT Support Agentic RAG application.

The main purpose is to load configuration values and API keys from a `.env` file, provide default values, manage application paths, validate configuration types, and make settings accessible throughout your application.

It uses three important Python libraries:

1. Pydantic Settings – Loads and validates environment variables.
2. Pathlib – Manages filesystem paths.
3. Functools (`lru_cache`) – Caches the settings object to avoid creating it repeatedly.

Let's understand it section by section.

## 1. Importing libraries

```
from functools import lru_cachefrom pydantic_settings import BaseSettings, SettingsConfigDictfrom pathlib import Path
```

| Library              | Purpose                                                |
| -------------------- | ------------------------------------------------------ |
| `lru_cache`          | Caches the settings object.                            |
| `BaseSettings`       | Reads environment variables and `.env` configurations. |
| `SettingsConfigDict` | Defines Pydantic configuration options.                |
| `Path`               | Handles directory and file paths.                      |

Why Pydantic Settings?

Instead of manually reading environment variables using `os.getenv()`, Pydantic automatically loads them, converts their values to the required types, and validates required settings.

## 2. Defining the base directory

```
BASE_PATH = Path(__file__).resolve().parent[2]
```

This is an important line.

Let's break it down:

- `__file__`: Location of the current `config.py` file.
- `.resolve()`: Converts the path into an absolute path.
- `.parent`: Gets the parent directory.
- `[2]`: Gets the third parent directory.

For example, suppose your project structure is:

```
Enterprise_IT_Support/
│
├── backend/
│   ├── app/
│   │   ├── core/
│   │   │   └── config.py
│   │   ├── main.py
│   │   └── ...
│   │
│   ├── .env
│
├── data/
├── uploads/
└── ...
```

If `config.py` is inside `backend/app/core/`, then:

```
Path(__file__).resolve().parent[2]
```

resolves to:

```
Enterprise_IT_Support/backend
```

Important: This depends on your actual folder structure. If the file is moved, you may need to change the parent index.

## 3. Settings class

```
class Settings(BaseSettings):
```

This class inherits from Pydantic's `BaseSettings`.

It acts as a centralized location for all application configurations.

Whenever you create an instance:

```
settings = Settings()
```

Pydantic automatically:

- Reads values from the `.env` file.
- Reads environment variables.
- Converts values into the declared Python types.
- Validates required fields.
- Applies default values when variables are missing.

```

| Variable   | Explanation                                                                |
| ---------- | -------------------------------------------------------------------------- |
| `APP_NAME` | Name of your application.                                                  |
| `APP_ENV`  | Current execution environment, such as Development, Testing or Production. |

For example, in your `.env`:

```
APP_NAME=Enterprise IT Support Agentic RAG
APP_ENV=Production

The `.env` values override the defaults.

### 3.4 RAG retrieval configurations

```
MAX_RETRIES: int = 1TOP_K: int = 10TOP_K_RANKED: int = 3
```

These parameters control retrieval and retry behaviour.

TOP_K = 10

Initially retrieve the top 10 documents from your vector database.

TOP_K_RANKED = 3

After reranking, retain the top 3 most relevant documents.

MAX_RETRIES = 1

Defines a retry-related configuration for your application. The actual retry behaviour depends on how you implement it elsewhere in your code.

Example RAG workflow:

User Query

Pinecone Vector Search

Retrieve TOP_K = 10 documents

Reranking

Select TOP_K_RANKED = 3 documents

LLM generates the answer

This is the intended retrieval flow based on these configuration names; the actual implementation depends on your retrieval code.

### 3.5 Security and filesystem configurations

```
ADMIN_API_KEY: str = 'load'AUDIT_DB_PATH: str = str(BASE_PATH/'data'/'audit.db')UPLOAD_DIR: str = str(BASE_PATH/'uploads')SAMPLE_KB_PATH: str = str(BASE_PATH/'data'/'sample_kb')
```

Let's understand each one.

| Variable         | Purpose                                                   |
| ---------------- | --------------------------------------------------------- |
| `ADMIN_API_KEY`  | API key intended for protecting administrative endpoints. |
| `AUDIT_DB_PATH`  | Location of the audit SQLite database.                    |
| `UPLOAD_DIR`     | Directory for uploaded documents.                         |
| `SAMPLE_KB_PATH` | Directory containing sample knowledge-base documents.     |

Understanding this expression:

```
str(BASE_PATH/'data'/'audit.db')
```

The `/` operator in `pathlib` joins directory and file names.

For example:

```
BASE_PATH = Path("/project/backend")AUDIT_DB_PATH = str(BASE_PATH/'data'/'audit.db')
```

Result:

```
/project/backend/data/audit.db
```

Converting it to `str()` gives a string path that can be passed to libraries expecting string paths.

Security recommendation: Do not use `'load'` as a production admin API key. Load a strong secret from the environment and validate that it is configured.

## 4. Pydantic model configuration

```
model_config = SettingsConfigDict(    title="Enterprise IT Support Agentic RAG",    env_file=str(BASE_PATH/'.env'),    extra='ignore')
```

This defines how Pydantic loads and processes your settings.

| Parameter        | Explanation                                                                        |
| ---------------- | ---------------------------------------------------------------------------------- |
| `title`          | Name of the settings model.                                                        |
| `env_file`       | Location of the `.env` file.                                                       |
| `extra='ignore'` | Ignores additional variables in `.env` that are not defined in the Settings class. |

For example, suppose your `.env` contains:

```
GROQ_API_KEY=your_key
HUGGINGFACE_API_KEY=your_key
SOME_UNUSED_VARIABLE=123
```

Since `SOME_UNUSED_VARIABLE` is not declared in the Settings class, it will be ignored.

This is useful when multiple components share one `.env` file.

## 5. Understanding `@lru_cache`

This is one of the most important parts of your configuration file.

```
@lru_cachedef get_settings() -> Settings:    return Settings()
```

Let's understand it step by step.

Without caching:

```
def get_settings():    return Settings()
```

Every time you call:

```
settings1 = get_settings()settings2 = get_settings()settings3 = get_settings()
```

Three separate Settings objects are created.

With caching:

```
@lru_cachedef get_settings() -> Settings:    return Settings()
```

The first call creates the Settings object. Subsequent calls reuse the cached object.

How caching works

First call: `get_settings()`

Creates Settings object

Settings object stored in cache

Subsequent calls

Reuse cached object

Example:

```
settings1 = get_settings()settings2 = get_settings()print(settings1 is settings2)
```

Output:

```
True
```

This is useful because:

- Configuration is loaded only once.
- Avoids repeatedly reading the `.env` file.
- Provides a consistent configuration object throughout your application.
- Reduces unnecessary object creation.

If you change `.env` while the application is running, the cached object will not automatically reload. You can clear the cache using:

```
get_settings.cache_clear()
```

## 6. How to use `get_settings()` in other modules

Suppose you have the following project structure:

```
backend/
│
├── app/
│   ├── core/
│   │   └── config.py
│   │
│   ├── services/
│   │   └── llm_service.py
│   │
│   └── main.py
│
└── .env
```

Inside `llm_service.py`:

```
from app.core.config import get_settingssettings = get_settings()groq_api_key = settings.GROQ_API_KEYgroq_model = settings.GROQ_MODEL
```

Inside `main.py`:

```
from app.core.config import get_settingssettings = get_settings()print(settings.APP_NAME)print(settings.APP_ENV)
```

You don't need to load `.env` independently in every module.

## 7. Important correction in your existing code

Your current code contains:

```
BASE_PATH = Path(__file__).resolve().parent[2]
```

This is incorrect because `Path.parent` returns a Path object, which is not subscriptable.

If you intend to access the third parent directory, use:

```
BASE_PATH = Path(__file__).resolve().parents[2]
```

Remember:

| Expression    | Meaning                    |
| ------------- | -------------------------- |
| `.parent`     | Immediate parent directory |
| `.parents[0]` | Immediate parent directory |
| `.parents[1]` | Grandparent directory      |
| `.parents[2]` | Third parent directory     |

Make sure `.parents[2]` points to the directory where your `.env`, `data`, and `uploads` directories are located.
