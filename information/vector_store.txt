Your code is following a singleton-style design pattern with lazy initialization. This is a good approach for an Agentic RAG application because embedding models, Pinecone connections, vector stores, and rerankers can be expensive to initialize.

However, your current implementation has a few issues:

1. `get_embedding_model()` creates a new embedding model every time it is called.
2. `embedding_model_dimension()` assumes `_embeddings` has already been initialized.
3. `get_vectorstore()` does not initialize embeddings before creating the vector store.
4. `add_documents()` assumes `_vectorstore` already exists.
5. `get_reranker()` creates a new CrossEncoder every time it is called.
6. `get_reranker()` uses `_vectorstore.invoke(query)` instead of explicitly using the configured retriever.
7. Your index deletion logic can delete an existing index containing valuable vectors if dimensions don't match. This should be handled carefully.

Let's understand the concepts first and then look at corrected code.

# 1. What is the purpose of `_embeddings = None`?

Consider:

```
_embeddings = None_vectorstore = None_reranker = None
```

These are global variables used to store objects that you want to initialize once and reuse throughout your application.

The underscore `_` at the beginning is a Python naming convention.

It means:

- This variable is intended for internal use within the module.
- It is not intended to be accessed directly by other modules.
- It is not private in the strict Python sense.

The `None` means that the object has not been created yet.

For example:

```
_embeddings = Nonedef get_embedding_model():    global _embeddings    if _embeddings is None:        _embeddings = HuggingFaceEmbeddings(            model_name="sentence-transformers/all-MiniLM-L6-v2"        )    return _embeddings
```

Let's understand what happens.

First function call

```
get_embedding_model()
```

None

Initialize model

Store model

`_embeddings` now contains the initialized model.

Second function call

```
get_embedding_model()
```

Model exists

Reuse model

No new model is created.

This is called lazy initialization because the model is initialized only when it is needed.

It also follows the singleton-style pattern because the same object is reused rather than creating multiple instances.

## 2. Why do we use `global _embeddings`?

Consider:

```
_embeddings = Nonedef get_embedding_model():    _embeddings = HuggingFaceEmbeddings(...)
```

This code does not update the global `_embeddings`.

Python treats `_embeddings` inside the function as a local variable because you assign a value to it.

To modify the global variable, you need:

```
def get_embedding_model():    global _embeddings    _embeddings = HuggingFaceEmbeddings(...)
```

Now Python knows that you want to modify the module-level variable.

Important: You only need `global` when assigning to the global variable. You don't need it merely to read the variable or call methods on its object.

For example:

```
def embedding_model_dimension():    return len(_embeddings.embed_query("What is AI?"))
```

No `global` is required here because you're only reading `_embeddings`.

Recommended implementation

# 5. Understanding each function in detail

## A. `get_embedding_model()`

```
def get_embedding_model():    global _embeddings    if _embeddings is None:        _embeddings = HuggingFaceEmbeddings(            model_name=_EMBEDDING_MODEL_NAME,            encode_kwargs={"normalize_embeddings": True}        )    return _embeddings
```

Purpose: Load the Hugging Face embedding model only once.

Suppose your application receives 100 user queries.

Without lazy initialization:

```
def get_embedding_model():    return HuggingFaceEmbeddings(        model_name=_EMBEDDING_MODEL_NAME    )
```

You could load the model 100 times.

With lazy initialization:

- First request: loads the model.
- Second request: reuses the model.
- Third request: reuses the model.
- 100th request: reuses the model.

This saves initialization time and memory.

## B. `embedding_model_dimension()`

```
def embedding_model_dimension():    embedding_model = get_embedding_model()    sample_vector = embedding_model.embed_query(        "What is AI?"    )    return len(sample_vector)
```

Why do we need this?

Pinecone requires you to specify the vector dimension when creating an index.

For example:

| Embedding model       | Typical dimension |
| --------------------- | ----------------- |
| all-MiniLM-L6-v2      | 384               |
| all-mpnet-base-v2     | 768               |
| BAAI/bge-base-en-v1.5 | 768               |

These are examples; always verify the actual output of your selected model.

Suppose your embedding model produces:

```
[0.12, 0.34, 0.56, 0.78]
```

The dimension is:

```
len(sample_vector)  # 4
```

Pinecone must be configured with the same dimension.

Important: The embedding model used to insert documents and the model used to embed queries must be compatible. Otherwise, similarity search won't work correctly.

## C. `ensure_index()`

This function performs three important tasks:

1. Checks whether the Pinecone index exists.
2. Checks whether its dimension matches your embedding model.
3. Creates the index if it doesn't exist.

Why do we need this?

Imagine your embedding model produces 384-dimensional vectors.

But your Pinecone index was created with 768 dimensions.

You cannot insert 384-dimensional vectors into a 768-dimensional index.

The corrected implementation raises an error rather than deleting your existing index.

Why is that important?

Your existing index may contain thousands of document vectors. Automatically deleting it could destroy your stored knowledge base.

## D. `get_vectorstore()`

```
def get_vectorstore():    global _vectorstore    if _vectorstore is None:        embedding_model = get_embedding_model()        index = ensure_index()        _vectorstore = PineconeVectorStore(            index=index,            embedding=embedding_model,            namespace=settings.PINECONE_INDEX_NAMESPACE        )    return _vectorstore
```

This is one of the most important functions.

It connects three components:

- Embedding model
- Pinecone index
- LangChain vector store

Think of it this way:

| Component             | Responsibility                   |
| --------------------- | -------------------------------- |
| HuggingFaceEmbeddings | Converts text into vectors       |
| Pinecone              | Stores and searches vectors      |
| PineconeVectorStore   | Connects LangChain with Pinecone |

Why use `_vectorstore = None`?

Because you don't want to create a new vector-store object every time you retrieve documents or insert chunks.

You initialize it once and reuse it.

## E. `add_documents(chunks)`

```

## G. `get_reranker_model()`

```

Why do we need another global variable?

Because CrossEncoder models can also be expensive to load.

For example:

```

```

First request:

```

```

Loads the CrossEncoder model into memory.

Second request:

```

```

Reuses the already loaded model.

You avoid loading the same model repeatedly.

## H. `rerank_documents(query)`

This is where the actual reranking happens.

First, understand why reranking is necessary.

Vector similarity search and reranking are two different operations.

Suppose the user asks:

"What is the process for resetting an employee password?"

Pinecone retrieves five documents based on embedding similarity.

| Document                             | Initial retrieval rank |
| ------------------------------------ | ---------------------- |
| Document A: Password policy          | 1                      |
| Document B: Employee onboarding      | 2                      |
| Document C: Password reset procedure | 3                      |
| Document D: Account security         | 4                      |
| Document E: VPN configuration        | 5                      |

But embedding similarity doesn't always identify the most relevant document.

The CrossEncoder evaluates the query and each retrieved document together.

It might produce:

| Document   | Reranker score | New rank |
| ---------- | -------------- | -------- |
| Document C | 9.5            | 1        |
| Document A | 8.2            | 2        |
| Document D | 7.1            | 3        |
| Document B | 5.4            | 4        |
| Document E | 2.1            | 5        |

Illustrative scores, not actual model output.

Then:

```
reranked_docs = rerank_documents(query, top_n=3)
```

Returns only the three most relevant documents.

### How does CrossEncoder work?

It takes two inputs:

1. User query
2. Document text

For example:

```
pairs = [    [        "How to reset employee password?",        "Employees can reset their passwords through the IT portal."    ],    [        "How to reset employee password?",        "VPN configuration requires administrator access."    ]]
```

Then:

```
scores = reranker.predict(pairs)
```

The model evaluates each query-document pair and generates a relevance score.

Unlike a bi-encoder embedding model, a CrossEncoder jointly processes the query and document. This generally provides better relevance ranking, although it is more computationally expensive.

### One important distinction: Singleton versus global variable

These concepts are related, but not identical.

- Global variable: A variable accessible throughout its module.
- Singleton pattern: A design approach that ensures only one instance of an object is created and reused.
- Lazy initialization: Creating the object only when it is first needed.

Your implementation combines all three concepts.

One limitation: Python module-level globals are shared within a single Python process, not across separate processes or servers. If you run four FastAPI workers, each worker can load its own embedding and reranking models.
